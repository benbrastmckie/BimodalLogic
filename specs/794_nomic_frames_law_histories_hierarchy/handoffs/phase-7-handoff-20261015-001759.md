## The first invariants run found five failures; four were mine

The dispatch warned that `check-paper-definitions.sh`'s exit 1 is inherited. That warning held
exactly — ten anchors, all pre-existing. But `check-module-invariants.sh` reported five failing
groups and **four of them were this task's own**, which is worth recording because none was
visible from a scoped build:

1. **C34a** — `mem_lawHist_iff_isStepPath`'s `Constraints consumed:` marker listed three
   constraints while its `[F.IsRegular]` binder supplies four, and no binder-free form exists.
   Corrected to all four, with the reason recorded at the declaration.
2. **C16** — the `unusedArguments` linter flagged `ofStepFamily`'s `[Finite W]`. The binder is
   pinned by the plan's Challenge statement and is what `ofStepFamily_isRegular` needs, so it was
   kept, documented at the declaration, and recorded in `scripts/nolints.json` — not silenced
   with an inline attribute, and `runLinter --update` was *not* run (it would grandfather
   everything currently reported).
3. **C23** — 39 `Uppercase_x` declaration names (`R1_fwd`, `F1_static`, …) outside the recorded
   leave-alone classes. All 39 renamed to the dotted form the gate itself suggests (`R1.fwd`,
   `F1.static`). One rebuild caught the 13 fully-qualified references inside `nomic_hierarchy`
   that the first rename pass skipped.
4. **INV** — stale generated inventory blocks in `FormalSystem/README.md` and `README.md`, since
   the file count moved 683 → 688. Repaired with `--emit-inventory`.
5. **C15** — `thm:nomic-primitive` resolved to nothing. The plan expected citing it as cut
   material by file and header to keep C15 out of it; C15 scans for anchor-shaped strings
   regardless of how they are framed. Fixed the gate's own way: a `DANGLING` `KNOWN-ANCHORS` row
   whose note records that the anchor is real but lives in `appendix_cut_material.tex`, which the
   record does not track, so `--resolve` structurally cannot read it.

The C23 rename required a second full `lake build` (~30 min), because touching `Witnesses.lean`
invalidates everything downstream of `Semantics.lean`. Unavoidable in sequence — the linter and
naming gates cannot run before the library is built — but a scoped C23/C16 pre-check at
first-module time would have caught both in Phase 1, before any full build existed.
