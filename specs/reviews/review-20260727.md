## High Priority Issues

### 1. No Dedekind-class countermodel — the ℚ-flowed Prior/Sep input model does not exist
**File**: `FormalSystem/Metalogic/BXCanonical/Completeness.lean:133`
**Description**: Reynolds' transfer route needs, as its step-1 input, a `ℚ`-flowed model
validating Prior-U / Prior-S / Sep. The tree's `countermodel_dense_enriched` produces a `ℚ`
model for `FrameClass.Dense` (`density` + `dense_indicator`) — a *different* axiom set. There
is no Dedekind-class analogue anywhere in `Metalogic/`.
**Impact**: This is the entry point of the whole completeness chain. Nothing downstream can be
attempted until it exists.
**Recommended fix**: Build a Dedekind-class analogue of `countermodel_dense_enriched` from a
Dedekind-MCS (phase 6). Note the structural warning below.

### 2. The Base-MCS trap applies verbatim to the Dedekind branch
**File**: `FormalSystem/Metalogic/BXCanonical/Completeness.lean:178-193`
**Description**: The file already documents why general `completeness` carries `sorryAx`: a
Base-MCS is not automatically Discrete-consistent. A Dedekind variant hits the structurally
identical problem — a Base-MCS need not validate Prior-U/Prior-S/Sep, so it is not
automatically Dedekind-consistent. The countermodel must be built from an MCS of its own class.
**Impact**: An implementer who reuses the dense pipeline's MCS will produce a proof that looks
complete and is unsound at the seam. This is the single most likely way this effort goes wrong.
**Recommended fix**: Any phase-6 plan must state the MCS class as a hard precondition and
verify it before the countermodel is assembled.

### 3. The Doets/transfer engine is ℤ-specialized with no dense analogue
**File**: `FormalSystem/Metalogic/WeakCanonical/IntegerModel/GoodStructures.lean`
**Description**: The right primitives exist (`good`, `VeryGood`, `ContempEquiv`,
`k_equiv_of_iso`, `KEquiv`, `orderedSumPt`), but the engine driving them is
`subinterval_finite_of_succ_archimedean` — a **finiteness** argument with no dense counterpart.
The real-flow route must replace it with Reynolds Theorems 4 and 5 (D1/D2) and then Theorem 6.
**Impact**: This is phases 7-8, rated **High** and **Highest**. It is new mathematics, not a
re-wiring task, and is the largest single cost in the remaining work.
**Recommended fix**: Treat phase 8 as the re-scope / possible-`[BLOCKED]` decision point, as
task 390's report already recommends. Do not plan it as a bounded phase.

## Medium Priority Issues

### 4. Weak vs. strong completeness — RESOLVED during this review, and it changes the verdict
**File**: `specs/390_dedekind_carrier_construction_research/reports/01_dedekind-carrier-construction.md:486`
**Description**: Reynolds Theorem 7 delivers explicitly **weak** completeness ("sound and
weakly complete", printed p.189). Task 390's report states that if the target is strong
completeness, "this route does not reach it and the verdict changes." Two active tasks
(361, 362) target strong completeness architecture across all frame classes.
**Resolution (decided 2026-07-27)**: **Strong completeness is the target; weak completeness is
to fall out as a corollary.** The verdict has therefore changed.
**Impact**: The Reynolds transfer route, as written in task 390's phase decomposition, does not
reach the goal. That decomposition is superseded as a plan of record. Whether the Reynolds route
extends to strong completeness — or whether a different construction is the faithful one — is
now the open question, not an execution detail.
**Status**: Task 408 created to determine the faithful route before any construction is planned.

### 5. The bimodal graft is unvalidated for the transfer argument
**Description**: Reynolds works with plain temporal structures; this tree is bimodal
(S5 ⊗ temporal) with `TaskFrame` / `WorldHistory` / `Omega` / `ShiftClosed`. Task 390 flagged
grafting a monadic-FO transfer argument onto history-indexed semantics as genuinely new work
not present in any source read.
**Impact**: Unknown-size risk sitting underneath phases 7-8.
**Recommended note**: The just-completed `sep_valid` work found the analogous graft *trivial*
for soundness — Sep's operators are all temporal at a fixed history, so it reduced to pure
order theory. **That result does not transfer to completeness**, where the construction must
produce histories rather than evaluate at one. Do not read the soundness outcome as evidence
the completeness graft is easy.

## Disposition

The weak-vs-strong question (issue 4) was settled during this review: **strong completeness is
the target, with weak completeness as a corollary.** That decision invalidates the terminus of
task 390's phase 6-9 decomposition, so none of those phases were scheduled.

The stated design constraint is to **avoid needless bridges** — prefer the construction that is
faithful to the mathematics over one that accumulates adapter lemmas and scaffolding to connect
artifacts the tree happens to already have. Under that constraint the phase-5 gap-freeness
bridge (issue 6) was deliberately **not** created as standalone work; it should appear only if
the faithful route genuinely requires it.

**One task created**: #408 — a literature-grounded research task to identify the most faithful
and mathematically correct route to strong completeness for `FrameClass.Dedekind`. It carries
issues 1, 2, 3, and 5 forward as named obstructions, records the settled target so the research
cannot terminate at weak completeness, and requires an explicit verdict — including an honest
"not currently reachable" if that is the answer.

Task 390 stays `[researched]`. It is the research artifact for a route whose terminus is no
longer the target; it is superseded as a plan of record but retained as evidence.
