## High Priority Issues

### H1. The four-language family is real and well-designed, but its layout hides it — including hiding that boxdot is already built

**Files**: `FormalSystem/Syntax/`, `FormalSystem/MinusLanguage/`, `FormalSystem/PlusLanguage/`, `FormalSystem/StarLanguage/`

**Description**: `Syntax/Formula.lean` (`L`: untl/snce primitive, box, boolean ops — the
language you said you care about most), `MinusLanguage/Formula.lean` (`L⁻`: H/G primitive
instead, related to `L` by an explicit translation), `PlusLanguage/Formula.lean` (`L⁺` = `L` plus
`⊡`), and `StarLanguage/Formula.lean` (`L⋆` = `L⁺` plus the hybrid time-register operators
`↑ⁱ`/`↓ⁱ`) form one deliberate extension hierarchy, each with a documented reason for being a
*separate inductive type* rather than more constructors bolted onto `Formula` (`StarFormula`'s
own docstring: adding store/recall to `PlusFormula` "would silently invalidate a landed
conservativity result"). This is good design, not disorganization — but it is filed as four
directories that are siblings of each other at `FormalSystem/` root, with nothing at that level
signaling that three of them are extensions of the fourth. Your instinct that "it would make
sense for all of this to live in `Syntax/`" is correct: nothing about the family requires them to
be flat siblings, and nesting them communicates the relationship the current layout doesn't.

**Impact**: You went looking for a place to add boxdot and didn't find that it already exists,
in a directory two levels away from `Syntax/` you'd have had no reason to open first. That is a
real cost, independent of anything file-organizational: it risks duplicate work on a proof that
was already carried through to soundness. The same discoverability gap will recur for the next
person (or the next session) who reaches for `Formula` and doesn't know `PlusLanguage/` and
`StarLanguage/` exist.

**Recommended fix**: Physically nest the three under `Syntax/` (e.g.
`Syntax/MinusLanguage/`, `Syntax/PlusLanguage/`, `Syntax/StarLanguage/`, alongside
`Syntax/Formula.lean` as the base case), and add a short "Language family" section to
`Syntax/README.md` (new) mapping each operator delta to its directory — this is the piece that
directly closes the boxdot-discoverability gap. This is **not** the kind of move
`docs/architecture/ADR-006-Metalogic-No-Physical-Regroup.md` declined: that ADR turned down
regrouping `Metalogic/`'s three completeness routes specifically because `WeakCanonical` alone
has 339 import lines across 137 files and the two routes are mutually cyclic at the directory
level — a half-updated move there would be worse than no move. Measured here instead: `import
FormalSystem.MinusLanguage.*` / `.PlusLanguage.*` / `.StarLanguage.*` appear in 7 + 11 + 6 = 24
files total (against `Syntax`'s own 67 importers, whose path does not change), and there is no
cycle — `Minus/Plus/Star` each import *from* `Syntax`/`PlusLanguage`, never the reverse. This is
a mechanical rename (update ~24 import lines, the 3 sibling aggregator files, the C8
parent-directory allowlist in `scripts/check-module-invariants.sh` — see L1 below — and the
README tables that list these as top-level directories), not a proof-bearing change; every
existing proof is preserved verbatim modulo the module-path rewrite.

**On `MinusLanguage/` specifically**: this review looked for whether it (and `StarLanguage/`,
which you also said you care less about) belongs in `Boneyard/` instead. It does not.
`Boneyard/README.md` defines that archive's admission criterion precisely: abandoned/refuted
approaches and unfinished (`sorry`-carrying) proofs — "the live tree is sorry-free... the archive
carries every `sorry` in the repository precisely *because* the live tree carries none."
`MinusLanguage/` is live, imported by 7 files, and sorry-free; it backs the documented
`L⁻`-soundness route and the backward-conservativity bridge. Caring less about a primitive
tense-only presentation is a legitimate reason to *deprioritize* work there, but it is not
evidence the code is dead, and archiving it would delete a landed, referenced result. Recommend:
keep it live, nested under `Syntax/` per the fix above.

### H2. `Semantics/Truth.lean` conflates the primary language's truth clauses with a separate correspondence topic — which is *why* it looked off-topic

**File**: `FormalSystem/Semantics/Truth.lean` (1,193 lines)

**Description**: The file does define `TruthAt` for `Formula` — the untl/snce/box/boolean
language you care about most — at lines 241–577, and that definition is exactly on-topic. But it
is under half the file. From line 623 to the end (~570 lines, 48%), the file shifts to a
different subject: `TruthCorr`, `TruthIso`, `TruthAntiIso`, `ShiftRel`, `shiftCorr`, and a
`TimeShift` namespace — machinery for when two task models' truth relations correspond or are
isomorphic under a time-shift, not clauses of `Formula`'s own truth definition. That *is* a
distinct concern, and the codebase already has a home for exactly this kind of material:
`Semantics/Correspondence/` (5 files: `Galois.lean`, `FwdRec.lean`, `FwdRecBridge.lean`,
`FwdRecPeriodicity.lean`, `Indicator.lean`, `DurationFrames.lean`) already collects
frame-correspondence results as its own subdirectory. `Truth.lean`'s isomorphism/shift apparatus
is the same kind of material, just not yet moved there.

**Impact**: Reading `Truth.lean` top-to-bottom to understand "how is truth defined for my
language" means wading through unrelated correspondence machinery to find and then leave the
~570 lines that actually answer that question. This is very plausibly the source of the
impression that the file "seems to focus not on the language I care most about" — it isn't
wrong that a large fraction of the file is about something else; it's that the something-else is
correspondence theory, not another language.

**Recommended fix**: Split `Truth.lean` at its existing internal seam (`TruthAt` +
its immediate corollaries stay; `ShiftRel`, `shiftCorr`, `TruthCorr`, `TruthIso`, `TruthAntiIso`,
and the `TimeShift` namespace move to a new `Semantics/Correspondence/TruthShift.lean` or
similar, joining the existing `Correspondence/` subdirectory). No proof content changes — this is
a pure file split with import-line updates in whatever currently reaches the moved declarations
via `Semantics.Truth`. Doing this also shrinks `Truth.lean` to a size that actually matches what
it's for.

### M3. `ForMathlib/` itself is correctly organized as-is — flagging so no effort is spent "fixing" it

**File**: `FormalSystem/ForMathlib/Order/PFilter.lean` (the sole file)

**Description**: You asked whether `ForMathlib/` needs to be there. It does, and its current
position (a top-level sibling directory under `FormalSystem/`, not nested inside `Syntax/` or
anywhere else) is intentional, not accidental. Its own module docstring states the dependency
rule `Mathlib → ForMathlib → FormalSystem`: it must import nothing from `FormalSystem.*`, and a
grep confirms it doesn't (`import Mathlib.Order.PrimeIdeal` / `Mathlib.Order.PrimeSeparator`
only). It is genuinely used — imported by `Init.lean`, the top-level `FormalSystem.lean`
re-export, and `Metalogic/Algebraic/UltrafilterMCS.lean` — for prime-filter API intended for
eventual upstreaming to Mathlib itself. Nesting it under `Syntax/` (or anywhere
language-specific) would misrepresent it as syntax-specific when it's a generic order-theory
extension; keeping it as its own top-level directory correctly signals "this is a one-way,
upstream-bound dependency layer," matching the same design principle (directory position =
dependency-direction signal) that `docs/architecture/ADR-006` uses to explain why `Metalogic/`'s
routes stay siblings. No structural change recommended.
