**File**: `.github/workflows/ci.yml:55`
**Description**: All three workflows set `use-mathlib-cache: true` (`ci.yml:55`, `docs.yml:92`,
`release.yml:115`), so Mathlib oleans are fetched rather than built. But there is **no
`actions/cache` step in any workflow** — no `actions/cache`, no `key:`, no `restore-keys`
anywhere under `.github/workflows/`.

**Impact**: Every CI run re-elaborates all 716 `FormalSystem` modules / 371,441 lines from
scratch. Local `.lake/build` is 6.3 GB, which is the scale of artifact being discarded per run.

two filed build-cost tasks, which target elaboration time inside one module and its fan-in rather
than cross-run artifact reuse.

**Recommended fix**: Add an `actions/cache` step keyed on the toolchain plus `lake-manifest.json`
plus a cache-epoch segment (the repo's own convention for epoch segments, e.g. `lake-recheck-v3-`,
is already a sanctioned durable version axis). Scope the restore to `.lake/build` only; Mathlib
stays on `use-mathlib-cache`.

### On the completeness literature gap

Stated plainly, because it bears on how L⁺ completeness should be scheduled: the suspicion that
the existing canonical-model machinery cannot reach TM⁺ is **confirmed and machine-grounded**, not
merely suspected. All four landed completeness engines build deterministic linear countermodels on
which `⊡` is the identity (`stab_iff_of_deterministic`), and
`Metalogic/Deterministic/Engines.lean` proves that narrowing is *free* because every countermodel
frame is a `multiFamTaskFrameGen` specialization. `BXCanonical/` and `WeakCanonical/` therefore
offer **no incremental path** to a TM⁺ canonical model — the required witness is structurally
different, and states must not be MCSs. Combined with the README's position that Reynolds 2003 and
Zanardo 1991 do not transfer, there is no known proof technique to schedule here. 559's
research-first framing is the right shape; an implementation task would be dishonest.
