**Why the semantic mode should be a separate thing**
- Principle 1 of the architecture record: a script shows what it builds, and no tactic name serves two tiers. The derivation proof mode makes one promise, that a script in it is a native derivation tree. This PR overloads about twenty of its tactic names (`lintro`, `lapply`, `lcases`, `lrewrite`, `lsimp`, `lstep`, `luntil`, `lprogress`, …) to act on truth goals as well, dispatching on the goal's shape. After that, a reader cannot tell from a script which kind of proof it is, and the promise is no longer visible where it matters.
- The two modes are coupled in code. The 31 handlers in `SemanticCore.lean` read the native tactics' syntax by raw index (`stx[1]`, `stx[3].getId`, `afterKeyword?`; lines 345-366 and 1002-1179), so a later edit to a native tactic's syntax would misparse silently. The semantic `register_lrewrite` handler runs first and makes the native error "rewrite declaration must return a native derivation" unreachable (`SemanticRewriting.lean:462-475`), and semantic rules are stored in the native registration table. `SemanticRewriting.lean:414` builds a placeholder native `Judgment` (`FrameClass.Base`, empty context) only to reuse occurrence lookup.
- The derivation mode is about to be measured: at gate one (M3) a fixed selection of library entries is proved again in the mode and compared with their reference proofs. That measurement is only meaningful if the tactics measured build derivations and nothing else.
- It is the largest of the three PRs and the least tested (below), and it would land before the derivation mode has its first client.

**Things to fix in the code when it comes back**
- Parse with quotation patterns throughout, as `SemanticRewriting` and `SemanticTransport` already do; no raw indexing.
- `lsimp` swallows every per-rule error to a trace and ends with "made no decreasing change" (`SemanticSimplification.lean:76-79,98`), and `(obligations := expose)` turns any `demandProof` failure into a goal (`SemanticRewriting.lean:363-369`). Elaboration errors should propagate, as requested on #7.
- "Certified transport" is not a closed set: any Lean function or `Iff` between two truth judgments is accepted without `with` (`SemanticTransport.lean:100-111,145-149`), so `FactTransport.apply c hR` passed as a plain function is accepted on a goal. That is sound, but the refusal of a fact transport on a goal is then a convention. Either restrict the accepted certificates or say this plainly in the guide.
- `resolveSemanticParameters` (`SemanticRewriting.lean:252-258`) takes the first matching local hypothesis for a Prop side condition, while `SemanticCore.lean:407` says hypotheses are never searched. Make the code and the comment agree.
- `lprogress` is `lapply` plus a goal-shape check. The occurrence premise lives only in `rank_progress*`, so nothing forces a user-supplied rule to have one, and there is no past mirror. Document the first and add the second.
- `ltime_reflect using d` on a native goal elaborates `d` in the semantic handler before declining (`SemanticTransport.lean:357-362`), so it is elaborated twice. Separate names remove this.
- Side goals from `settleHoles` are left as natural metavariables (`SemanticTransport.lean:205-206`); make them synthetic opaque so they cannot be assigned by accident.
- Several messages do not name the command that raised them (for example `SemanticCore.lean:492,993`).
- The `+4/−2` change to native `Rewriting.lean` (the optional `resolveParameters` hook) exists only for the semantic caller and should go once the modes are separate.

The run with the lemmas alone is the control: if the lemmas give the saving, the tactic language has no client there.
