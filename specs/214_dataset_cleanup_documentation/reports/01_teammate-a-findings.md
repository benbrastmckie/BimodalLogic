## Key Findings

### 1. Dataset Generation Pipeline Architecture

The data/ directory is populated by **three distinct generation pipelines**, each producing different artifact types:

**Pipeline 1: Training Data (Lean → JSONL)**
- Executable: `lake exe dataset_generator` (root: `Bimodal.Automation.DatasetExport`)
- Source: `Theories/Bimodal/Automation/DatasetExport.lean`
- Orchestrated by: `scripts/run_dataset_generation.sh`
- Produces: `bmlogic-{medium,deep}.jsonl` + companion `_metadata.json`
- Metadata struct: `DatasetMetadata` in DatasetExport.lean — simple field set (9 fields)

**Pipeline 2: Benchmark Assembly (Lean → Python → JSONL)**
- Multi-stage: `benchmark_anchors` → `curate_benchmark.py` → `benchmark_oracle` → `finalize_benchmark.py`
- Produces: `bmlogic-bench.jsonl` + `bmlogic-bench_metadata.json`
- Metadata: Rich schema generated by `finalize_benchmark.py` (Python) — 12+ top-level fields with nested distributions

**Pipeline 3: Proof Step Extraction (Lean → JSONL)**
- Executable: `lake exe proof_extractor` (root: `Bimodal.Automation.ProofStepExport`)
- Produces: `proof_steps.jsonl` only (NO metadata file)
- Entirely different record schema (theorem-centric, not formula-centric)

### 3. Schema Analysis — JSONL Record Fields

**Training datasets (bmlogic-deep, bmlogic-medium)** — 11 fields:
`augmentation, countermodel, formula_ast, formula_str, frame_class, id, label, metrics, pattern_key, proof_trace, split`

**Benchmark dataset (bmlogic-bench)** — 13 fields:
`benchmark_category, countermodel, difficulty_tier, formula_ast, formula_str, frame_class, id, label, metrics, pattern_key, proof_trace, source, split`

**Proof steps (proof_steps)** — 8 fields:
`axiom_name, context, frame_class, goal, rule, step_index, subgoals, theorem_name`

**Key differences:**
- Benchmark adds: `benchmark_category`, `source`, `difficulty_tier` (benchmark-specific)
- Benchmark removes: `augmentation` (training-specific)
- Training has `augmentation` (null for originals, populated for temporal duals)
- Proof steps share only `frame_class` with the formula datasets — completely different schema

### 4. Metadata Schema Gap

The metadata files show a **dramatic quality gap**:

**bmlogic-bench_metadata.json** (rich — 12 top-level fields):
- `benchmark_name`, `version`, `description`, `generation_date`, `schema_version`
- `frame_class`, `total_count`, `valid_count`, `invalid_count`, `valid_ratio`
- `tier_distribution` (nested), `category_distribution`, `source_distribution`
- `anchor_coverage` (nested), `near_miss` (nested), `quality` (nested)

**bmlogic-{deep,medium}_metadata.json** (simple — 9 fields):
- `total_records`, `valid_count`, `invalid_count`, `timeout_count`
- `avg_complexity`, `include_duals`, `max_complexity`, `sampling_mode`, `frame_class`
- Missing: `version`, `description`, `generation_date`, `schema_version`, `quality`
- The metadata struct also declares a `representations` array in the serializer but the actual records don't have `formula_sexpr`, `formula_tokens`, or `pattern_features` fields — the representations field is aspirational/misleading

**proof_steps** — NO metadata file at all.

### 5. .gitignore Issue

The current `data/.gitignore` blanket-excludes ALL `.jsonl` and `*_metadata.json` files. This means **no datasets are tracked by git**, including the final ones. The task description says to "track final datasets while excluding intermediates" — this requires inverting the gitignore logic.

### 6. Scripts Directory

Seven Python/shell scripts in `scripts/` relate to dataset generation:
- `run_dataset_generation.sh` — Orchestrates training dataset generation
- `generate_dataset.py` — Converts JSON to PyTorch tensors
- `curate_benchmark.py` — Benchmark curation step
- `finalize_benchmark.py` — Final benchmark assembly with rich metadata
- `validate_benchmark.py` — Benchmark validation
- `verify_benchmark.py` — Post-export verification
- `swap_untl_snce.py` — Until/Since convention swap utility

## Recommended Approach

### Phase 1: Remove Intermediates (5 min)
```bash
rm data/axiom-instances.jsonl data/bmlogic-bench-candidates.jsonl \
   data/bmlogic-bench-validated.jsonl data/test.jsonl data/test_c4.jsonl \
   data/test_metadata.json data/test_c4_metadata.json
```

### Phase 2: Standardize Metadata (1-2 hours)
**Do NOT modify the Lean `DatasetMetadata` struct.** The Lean code generates the simple format; changing it requires rebuilding the struct, serializer, and re-running generation. Instead:

1. **Write a Python script** (`scripts/standardize_metadata.py`) that reads each simple `_metadata.json` and enriches it to match the bench format:
   - Add `dataset_name`, `version`, `description`, `generation_date`, `schema_version`
   - Add `quality` block (verify zero duplicates, label consistency)
   - Add `complexity_distribution` (scan the JSONL for tier stats)
   - Remove the misleading `representations` field from the Lean serializer (or document it as aspirational)

2. **Create `proof_steps_metadata.json`** with theorem inventory, rule distribution, step count, etc. (derivable from the JSONL itself).

### Phase 3: Fix .gitignore (10 min)
Replace `data/.gitignore` with explicit tracking:
```gitignore

# Final datasets are tracked by git (not ignored)
```

**Alternative**: Use root `.gitignore` patterns and delete `data/.gitignore` entirely.

### Phase 4: Create data/README.md (1 hour)
Document:

- Record schema for each dataset type (with field descriptions)
- Pipeline diagram showing generation flow
- Usage examples (Python loading, filtering)
- Regeneration instructions

### Phase 5: Verify Schema Consistency (30 min)
Run a validation script to confirm:
- All bmlogic-deep records have exactly 11 expected fields
- All bmlogic-medium records have exactly 11 expected fields
- All bmlogic-bench records have exactly 13 expected fields
- All proof_steps records have exactly 8 expected fields
- No null values in required fields (id, formula_str, label/rule)

This is dead/aspirational metadata that should be removed or the fields actually implemented.
