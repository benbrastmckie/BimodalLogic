# Research Report: Task #214

**Task**: Dataset cleanup, standardization, and documentation
**Date**: 2026-05-29
**Mode**: Team Research (4 teammates)
**Session**: sess_1780089949_bc0731

## Summary

The data/ directory contains 17 files produced by 3 distinct generation pipelines (training, benchmark, proof-steps). Seven files are intermediates or test artifacts that should be deleted. The remaining 4 final datasets (benchmark, deep, medium, proof_steps) have inconsistent metadata schemas — the benchmark has 14+ rich metadata fields while training datasets have 9 simple fields and proof_steps has no metadata at all. The current `data/.gitignore` blanket-excludes ALL data files, working against the task's goal of tracking final datasets. The recommended approach is: delete intermediates, create a common metadata header with dataset-specific extensions, write a HuggingFace-compatible README, fix gitignore with Git LFS for large files, and create proof_steps_metadata.json. The task is well-scoped for 4-6 hours but should coordinate with task 213 (actively regenerating datasets) and design documentation to be regeneration-aware rather than encoding frozen record counts.

## Key Findings

### Primary Approach (from Teammate A)

**Three distinct generation pipelines** populate the data/ directory:

1. **Training pipeline** (Lean → JSONL): `lake exe dataset_generator` via `scripts/run_dataset_generation.sh`. Produces bmlogic-{medium,deep}.jsonl with simple 9-field metadata via the `DatasetMetadata` Lean struct.

2. **Benchmark pipeline** (Lean → Python → JSONL): Multi-stage — `benchmark_anchors` → `curate_benchmark.py` → `benchmark_oracle` → `finalize_benchmark.py`. Produces bmlogic-bench.jsonl with rich 14+ field metadata generated by Python.

3. **Proof step pipeline** (Lean → JSONL): `lake exe proof_extractor`. Produces proof_steps.jsonl with NO companion metadata.

**File classification**: 7 files to keep (4 datasets + 3 metadata files), 7 to remove (3 benchmark intermediates + 4 test files), plus data/.gitignore to rewrite.

**Schema analysis**: Benchmark records have 13 fields (adds benchmark_category, source, difficulty_tier). Training records have 11 fields (adds augmentation). Proof steps have 8 completely different fields (theorem_name, step_index, context, goal, rule, axiom_name, subgoals, frame_class). Only `frame_class` is shared across all three types.

**Notable finding**: The Lean `datasetMetadataToJson` serializer declares `formula_sexpr`, `formula_tokens`, `pattern_features` in a `representations` array that the actual JSONL records don't contain — this is aspirational/misleading dead metadata that should be removed.

**Recommended implementation**: Python-based metadata enrichment script (avoid modifying Lean structs, which would require rebuilding and re-running generation). Five phases: remove intermediates → standardize metadata → fix gitignore → create README → validate schemas.

### Alternative Approaches (from Teammate B)

**Metadata standards (2026 landscape)**:
- HuggingFace Dataset Card (YAML frontmatter + Markdown) — dominant standard, recommended for README.md
- Croissant 1.1 (JSON-LD, MLCommons Feb 2026) — stretch goal, not required
- Datasheets for Datasets (Gebru) — overkill for auto-generated formal logic data

**Storage recommendation**: Hybrid Git + LFS. Track small files directly (bench 672KB, medium 4.2MB, all metadata), Git LFS for large files (deep 51MB, proof_steps 15MB). DVC is overkill for 4 files.

**Comparable datasets**: Lean Workbook, FIMO, HolStep, Spark-Prover-X1 all use explicit splits, provenance tracking, and difficulty stratification. BMLogic's benchmark already follows these patterns well; training datasets lag behind.

**Directory structure**: Flat layout preferred over subdirectories — only 4 datasets don't warrant navigational overhead. README provides conceptual grouping. Avoids breaking existing script paths.

**Unified metadata schema**: Common header (dataset_name, version, description, schema_version, generation_date, generator_version, lean_version, frame_class) + statistics section + parameters section (where applicable) + quality block + fields array documenting the record schema.

### Gaps and Shortcomings (from Critic)

1. **axiom-instances.jsonl is a pipeline input**, not purely intermediate — it feeds the Python curation step (`curate_benchmark.py` loads it alongside production data). While regenerable via `lake exe benchmark_anchors`, it has independent reference value showing all 724 axiom schema instantiations. The task should explicitly decide whether to keep it or document its regeneration.

2. **51MB deep dataset will bloat git** if tracked directly — every regeneration (task 213 plans to do this) creates a new 50MB+ commit. After 3-4 regenerations, data/ alone adds 150-200MB to git history. Git LFS or external hosting is necessary.

3. **Schema standardization won't work as a single format** — proof_steps has zero shared fields with formula datasets (except frame_class). The bench metadata format (tier_distribution, anchor_coverage, etc.) is meaningless for training data. A common header + dataset-specific extensions is the right model.

4. **Task 213 is actively regenerating datasets** — it's [IMPLEMENTING] and will overwrite deep and medium datasets. Documentation that freezes current record counts will be immediately stale. Design docs to be regeneration-aware: document schemas and generation commands, not frozen statistics.

5. **No checksums or integrity verification** mechanism planned — SHA-256 checksums in metadata would enable quick verification that files haven't been corrupted.

6. **gitignore negation patterns are fragile** — switching from "ignore all" to "ignore all except finals" via `!` patterns breaks when new intermediate files are added by future pipeline runs. Better: list specific intermediates to ignore rather than blanket-exclude with exceptions.

7. **Schema evolution not addressed** — no schema_version in training metadata; what happens when new fields are added to the generator?

### Strategic Horizons (from Horizons)

**The datasets are a genuinely novel publishable research artifact**: the first formally verified training data for decidable non-classical logics. No comparable datasets exist — LogiQA and ProofWriter cover propositional/FOL fragments; nothing covers temporal + modal + Until/Since. The cleanup should be designed with external consumption in mind from day one.

**Cross-project value**: These datasets could serve formal logic ML research, Lean tactic prediction research, curriculum learning research (medium → deep → bench difficulty progression), and logic education.

**Task 213 synergy**: Task 214 should establish the metadata and schema standard that task 213 also follows. If 214 runs first and defines the target format, 213's outputs can conform to it.

**Clean-break refactor target (6-month vision)**: Subdirectory-per-purpose structure (bmlogic-bench/, bmlogic-train/, bmlogic-proofs/) with per-type schema.json files, HuggingFace dataset cards per subdirectory, and Zenodo DOI-bearing snapshots alongside publication. But this is over-scoped for 4-6 hours — the current task should focus on the practical cleanup while establishing forward-compatible conventions.

**External distribution (future)**: HuggingFace Hub as `logos-labs/bmlogic-bench` and `logos-labs/bmlogic-train` with streaming support. Zenodo for versioned DOI archive. Current JSONL format is already optimal for HuggingFace.

## Synthesis

### Conflicts Resolved

1. **Git tracking for large files**: Teammate A implied direct git tracking; B and D recommended Git LFS for files >10MB; C recommended keeping large files gitignored entirely. **Resolution**: Git LFS is the pragmatic middle ground. It addresses C's repo bloat concern while ensuring datasets are version-tracked (B/D's recommendation). Pure gitignoring (C's preference) risks losing datasets if the build environment changes or the Lean version advances. **Adopt Git LFS for bmlogic-deep.jsonl (51MB) and proof_steps.jsonl (15MB); direct git for smaller files.**

2. **axiom-instances.jsonl disposition**: A classified it as REMOVE; C flagged it as a pipeline input with independent reference value. **Resolution**: Delete it but document regeneration command (`lake exe benchmark_anchors`). It IS regenerable and keeping intermediates contradicts the cleanup goal. Add a note in README about pipeline stages and how to regenerate intermediates.

3. **Directory structure**: B recommended flat; D proposed subdirectory-per-purpose. **Resolution**: Flat structure for this task (only 4 datasets, minimal navigational benefit from subdirectories, avoids breaking existing script paths). D's subdirectory vision is a future enhancement for external distribution, not a 4-6 hour task.

4. **Documentation approach**: C warned that documenting frozen record counts becomes stale when task 213 regenerates. **Resolution**: Document schemas and generation commands as primary content. Include current record counts as metadata fields (automatically updated by generation scripts) rather than hardcoded in README prose.

### Gaps Identified

1. **Git LFS configuration status**: No teammate checked whether Git LFS is already configured in the repository. This needs verification before implementation.
2. **Task 208 (HuggingFace packaging)**: Referenced by C and D as a future distribution mechanism but not researched. Its scope may overlap with documentation work in task 214.
3. **Lean metadata struct modification**: A identified the misleading `representations` field in `DatasetExport.lean`. Whether to fix the Lean code (simple deletion) vs document it as aspirational is unresolved — fixing it is quick but triggers a rebuild.
4. **Checksums**: C suggested SHA-256 in metadata. Good practice but may be over-scope for 4-6 hours. Could be a future enhancement or added to the generation scripts.

### Recommendations

**Core implementation (fits 4-6 hours)**:
1. Delete 7 intermediate/test files
2. Create `proof_steps_metadata.json` with appropriate fields (theorem count, rule distribution, step statistics)
3. Enrich training metadata with common header fields (dataset_name, version, description, generation_date, schema_version) via Python script — do NOT modify Lean `DatasetMetadata` struct
4. Rewrite `data/.gitignore` to list specific intermediates (not blanket exclusion with exceptions)
5. Set up Git LFS for bmlogic-deep.jsonl and proof_steps.jsonl
6. Write `data/README.md` in HuggingFace dataset card format (YAML frontmatter + structured Markdown) with schemas, generation instructions, and dataset descriptions
