
NOT the unconditional:

```
∀ φ, valid φ → Nonempty (DerivationTree [] φ)
```

`NoUnivBurgessR3` states: for all MCS pairs A, C, `¬burgessR3 A Set.univ C`. This says Set.univ is not a valid interval DCS for any pair of MCS — which should follow from the fact that Set.univ is inconsistent (contains both φ and ¬φ), and the burgessR3 definition requires the DCS to be deductively closed (hence consistent if ≠ Set.univ). **Impact**: Even after closing the 2 ChronicleConstruction sorry sites, `bx_completeness` will still have `sorryAx` in its axiom dependencies unless `NoUnivBurgessR3` is separately proved. The plan's Phase 5 validation criterion (`#print axioms bx_completeness` shows no `sorryAx`) CANNOT be met by closing just the 2 sorry sites. This is a **blind spot** in the plan.

**Difficulty assessment**: Probably straightforward — if Set.univ is inconsistent (it contains bot), and burgessR3's definition requires a DCS, then Set.univ being a DCS that is inconsistent should yield a contradiction since `∀ β ∈ Set.univ, ∀ γ ∈ C, U(γ, β) ∈ A` for MCS A would require all formulas to be in A, contradicting A being consistent. But it's still work that needs to be tracked.

### 2. The DC(B ∪ {xi}) Seed Strategy Is Sound But Has a Subtle Requirement

The handoff proposes changing lemma_2_7's Zorn seed from B to DC(B ∪ {xi}). The consistency argument is:

1. D is MCS (from Lindenbaum extension)
2. xi ∈ D (from seed membership)
3. B ⊆ D (from seed membership)
4. Therefore {xi} ∪ B ⊆ D (MCS ⊇ consistent set)
5. Therefore DC({xi} ∪ B) is consistent (subset of consistent set's deductive closure)

**Challenge**: Step 4→5 requires a lemma: if S is consistent (S ⊆ some MCS) and T = DC(S), then T is consistent. This is standard (`deductiveClosure_of_consistent_is_consistent` or similar), but I did NOT find this lemma in the codebase. Let me verify:

Actually, looking more carefully at the code (PointInsertion.lean:3692), `burgessR3Maximal_extension_exists` takes `h_B_dcs : SetDeductivelyClosed B` — so the seed must already be a DCS. The claim is to pass `DC(B ∪ {xi})` which is definitionally a DCS. The consistency requirement is that the DCS is not Set.univ (i.e., consistent), which follows from {xi} ∪ B ⊆ D and D being MCS (hence consistent). This is sound.

**However**, there's a practical gap: does `burgessR3Maximal_extension_exists` check consistency via `h_no_univ_AD` (which is about A and D, not about the seed)? Looking at the code:

```lean
obtain ⟨B', h_B_sub_B', _, h_B'_max⟩ := burgessR3Maximal_extension_exists h_mcs_A h_D_mcs
    h_B_dcs h_r3_ABD h_no_univ_AD
```

Yes — `h_no_univ_AD : ¬burgessR3 A Set.univ D` is about the pair (A, D), not about the seed's consistency directly. The Zorn argument starts from the seed and extends it; the `h_no_univ_AD` prevents the chain from reaching Set.univ. So the strategy works: start from DC(B ∪ {xi}) which satisfies burgessR3(A, DC(B ∪ {xi}), D) (this must be proved), and let Zorn extend to B'. Since B ∪ {xi} ⊆ DC(B ∪ {xi}) ⊆ B', we get xi ∈ B'.

**Key missing proof obligation**: `burgessR3 A (DC(B ∪ {xi})) D`. The handoff sketches this via `dc_delta_B_burgessR3` + `burgessR(A, β ∧ xi, D)` for β ∈ B. This appears sound mathematically. The code path needs:
- For all γ ∈ DC(B ∪ {xi}): `burgessR(A, γ, D)` — i.e., `∀ δ ∈ D, untl(δ, γ) ∈ A`
- DC(B ∪ {xi}) is generated by B ∪ {xi}, so it suffices to show `burgessR(A, β ∧ xi, D)` for β ∈ B and use BX3 right-monotonicity.

The handoff claims this follows from the existing seed memberships. This is plausible but needs careful verification that the BX3 right-monotonicity step (`⊢ β ∧ xi → γ` for γ ∈ DC(B ∪ {xi})`) is available in the right form.

### 3. The h_actual g-Value Change Has Cascading Effects

The current code has `h_actual` checking f-values. The handoff proposes changing to g-values. This affects:

**The "not actual" case (line 1470-1487)**: Currently produces:
```lean
c5_forward_witness := by
    push_neg at h_actual
    obtain ⟨y, hy_dom, hy_lt, hy_η, _⟩ := h_actual h_mem h_until
    exact ⟨y, hy_dom, hy_lt, hy_η⟩
```

After the change, `push_neg at h_actual` would give `∃ y ∈ χ.dom, pc.x < y ∧ pc.η ∈ χ.f y ∧ pc.ξ ∈ χ.g pc.x y` — which includes the guard! The discarded `_` would now be `pc.ξ ∈ χ.g pc.x y` instead of the old f-value condition. This witness directly provides the guard in g, which is exactly what's needed for the limit propagation.

**The "actual" case**: Now means "NO y exists with both η ∈ f(y) AND ξ ∈ g(x,y)". This is a STRONGER actuality condition (harder to be "actual"), meaning some cases that were previously "actual" are now "not actual". The set of actual counterexamples shrinks. This is fine — fewer counterexamples need elimination, and the ones that are eliminated now truly need structural intervention.

**Forward walk logic (lines 795-830)**: The walk checks `h_cond_i : Formula.and pc.ξ (Formula.untl pc.ξ pc.η) ∈ χ.f x' ∧ pc.ξ ∈ χ.g pc.x x'`. This is already g-value aware (the second conjunct checks guard in g). **However**, the `h_actual` condition is used at the walk's endpoint to extract the witness. After the change, the walk termination condition differs: the negation of h_actual now gives a different decomposition.

**Walk Case B "eta ∈ f(u_next)" shortcut (line 984-1004)**: Currently returns the chronicle unchanged with `u_next` as witness but NO guard. After the h_actual change, this shortcut is **problematic**: `u_next` has `η ∈ f(u_next)` but we don't know if `ξ ∈ g(x, u_next)`. If c5_forward_witness is strengthened to include guard, this case can no longer take the shortcut. It would need to prove `ξ ∈ g(pc.x, u_next)`, which is not trivially available.

**Risk**: The Walk Case B eta-shortcut needs significant rework. The current code takes 20 lines and is trivial; with the guard requirement, it may need a splitting proof or a different argument entirely. The handoff estimate of "~230 lines" may undercount this.

### 4. The c5_forward_witness Type Must Change

The current `EliminationResult.c5_forward_witness` type is:
```lean
c5_forward_witness : pc.kind = .c5_forward → pc.x ∈ χ.dom →
    Formula.untl pc.ξ pc.η ∈ χ.f pc.x →
    ∃ y ∈ val.dom, pc.x < y ∧ pc.η ∈ val.f y
```

It needs to become:
```lean
c5_forward_witness : pc.kind = .c5_forward → pc.x ∈ χ.dom →
    Formula.untl pc.ξ pc.η ∈ χ.f pc.x →
    ∃ y ∈ val.dom, pc.x < y ∧ pc.η ∈ val.f y ∧ pc.ξ ∈ val.g pc.x y
```

This is a **structural change** affecting ALL 18+ cases that provide `c5_forward_witness`. Many of these are for non-C5 counterexample types and provide `fun h => absurd h (by decide)`, which will still work since the type is stronger (proving ∃ with more conjuncts from absurd). But the actual C5 cases (lines 749, 919, 994, 1172, 1406, 1476) all need updating.

**However**, there's a subtler issue: `omega_chain_c5_witness` (ChronicleConstruction.lean:392) currently returns `∃ y, x < y ∧ η ∈ f(y)`. It would need to return `∃ y, x < y ∧ η ∈ f(y) ∧ ξ ∈ g(x,y)`. This requires the EliminationResult to carry the guard witness, and `limit_satisfies_c5_strong` can then combine the endpoint witness with the guard witness. This is the correct architecture but requires threading through the omega chain infrastructure.
