## What NOT to Try

- Do NOT run a bare `git stash` (or `git stash pop`) on this shared working tree while concurrent
  sibling tasks are dispatched. It stashes the ENTIRE tree, including siblings' uncommitted work
  in unrelated task directories and shared files (TODO.md, state.json, events.jsonl), and a
  `stash pop` can then conflict with a sibling's fresh edit made while the stash was held,
  stranding everything in the stash. If isolation of a single file's baseline is genuinely needed,
  use `git show HEAD:<path>` (read-only) or `git diff <path>` instead of stashing, or restore
  narrowly from the stash via `git show stash@{N}:<path> > <path>` for only the paths this task
  owns — never a blanket pop/apply. See progress file `phase-1-progress.json`'s
  `approaches_tried` entry for the concrete incident.
- Do not add `flock -u` after the C1 builds — it is deliberately omitted so later `.lake`-reading
  checks inherit the lock (see Key Decisions above).

## Addendum (post-hoc correction, added after task completion)

The "What NOT to Try" entry above understated the actual damage. The bare `git stash`/`git stash
pop` DID lose sibling data: `specs/events.jsonl` — an append-only, unowned, no-conflict file that
nobody's `file_scope` names — was silently reverted to its pre-stash HEAD state by the failed
pop, dropping 32 rows of real telemetry (including `lifecycle_stage`/`session_stop` events from
this task's own research-phase session and from an earlier session). This was NOT caught by the
recovery described above: extracting this task's 3 owned files from the stash via `git show
stash@{0}:<path> > <path>` and confirming `git status` showed no sibling *source* file touched
looked like a complete recovery, but it missed the unowned append-only file entirely, precisely
because it never showed up as a conflict (appends don't collide) and nothing in this task's own
declared scope pointed at it. A teammate (the orchestrating lead) caught the row-count regression,
recovered the 32 rows from the still-present `stash@{0}`, verified zero conflicting `event_id`s
between the two versions, merged the union deduped by `event_id` and sorted by timestamp (3413
rows total, nothing dropped from either side), and installed it before postflight committed the
file. No task data was ultimately lost, but only because of that follow-up catch, not because the
original recovery was sound.

The corrected lesson: selective post-hoc extraction of only your own declared files is NOT
sufficient recovery from a bare stash on a shared tree, because an unowned, append-only,
no-conflict file gives no signal that it was touched at all. The durable fix is to never bare-stash
a shared tree in the first place — see the corrected memory candidate in this task's final
`.return-meta.json` for the generalized form of this lesson.
