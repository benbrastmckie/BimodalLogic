## Key Decisions Made

- Switched the probe's concurrency mechanism from `Task.spawn` (tried first, confirmed via
  `/proc/<pid>/task/*/stat` polling on a compiled build to never use more than one thread on this
  toolchain regardless of `LEAN_NUM_THREADS`, including at `Task.Priority.dedicated`) to
  `IO.asTask` (confirmed via the same polling method to achieve genuine multi-thread concurrency).
  Both are named as acceptable by the plan's own task wording.
- Recorded verdict: **inconclusive**, not confirmed and not refuted. The official measurement
  (48-way flat, simultaneous fan-out under `lake env lean --run`) showed CPU utilization of 1433%
  (LEAN_NUM_THREADS unset) vs 1669% (=1) -- no capping signal, and if anything backward. This is
  attributed to the probe's own task shape (instantaneous, non-nested, flat fan-out) likely
  triggering the Lean runtime's own documented "not a hard limit; may be exceeded to avoid
  deadlocks" pool-size escape valve, which is a different shape from Lake's actual
  dependency-graph-driven job release. A Lake maintainer (Mac Malone, leanprover-community Zulip
  thread "number of threads for lake build") is on record stating Lake has no way to limit its own
  Task pool and that `LEAN_NUM_THREADS` "serves a good-enough fix for the few places this has been
  an issue" -- direct, named endorsement of the mechanism's practical effectiveness, independent of
  this probe's inconclusive result. Full reasoning is in `probe-results.md`.
- `nproc`=24 on this host; toolchain confirmed as `Lean (version 4.33.0-rc1, ...)` matching the
  pinned CI toolchain.
