### The registry mechanism: decision

Three designs were weighed.

| Design | Rows kernel-checked | Edits `FormalSystem` | Verdict |
|---|---|---|---|
| A. Attribute on each declaration, rows in an environment extension | no | yes: 190 declarations tagged, and the attribute must be declared in `FormalSystem/Tactic/Attr.lean` because `FormalSystem` cannot import `BimodalLib` | rejected |
| B. Hand-written rows under `BimodalLib/Theorems/<Fragment>/` | yes | no | rejected: the statement would be copied by hand |
| C. `register_theorem X` in modules under `BimodalLib/Theorems/<Fragment>/`, each expanding to a kernel-checked `def` built from the type of `X` | yes | no | **recommended** |

Design A fails twice. Its rows are reports, not checks; and it puts library bookkeeping into
the published library, against the import direction the record fixes. Design C keeps both
properties the description asks to weigh: the row is a term the kernel has checked, and the
statement is read from the declaration, not retyped.

The row type, as prototyped (`probes/registry-prototype.lean`):

```lean
structure TheoremEntry where
  arity : Nat
  frameClass : FrameClass
  stmt : (Nat → Formula) → Formula
  proof : ∀ fc, frameClass ≤ fc → ∀ v, DerivationTree fc [] (stmt v)
  profile : Profile                       -- box / stab / temporal occurrence
  profile_eq : profileF (stmt schemaVar) = profile
```

What the kernel checks in a row: `proof` cites the registered declaration and has the stated
type, so `stmt` IS the statement and `frameClass` is a class at which it is derivable;
`profile_eq` is closed by `rfl`, so the fragment and operator set are computed, not asserted.
`register_theorem X` reads `X`'s type, substitutes `v 0, v 1, ...` for the formula binders,
picks the frame class from the binder shape (inserting `DerivationTree.lift` for a fixed
class), reduces the profile, and adds the definition. Rows are named
`BimodalLib.Registry.<full name of X>`.

The registry is the set of constants of type `TheoremEntry`. Nothing is stored in an
extension, so the completeness check and the index read the same kernel-checked terms. The
completeness check reads the registered declaration off each row's `proof` field.

One limit, stated plainly: `frameClass` is the class the registered derivation is stated at.
For the 174 rows at Base that is the weakest class there is. For the 16 rows above Base
(5 by hypothesis, 11 fixed at ZTime) the row proves derivability at that class and does not
prove failure below it; "weakest" there is the author's claim, and becomes a checked fact only
when a countermodel entry at the lower class exists (`theorem_library_countermodels`).

## Decisions

- **No `user_decision` raised.** The `defaultTargets` question is answered by the record; the
  description's request for a ruling predates that. Recorded in the issue log.
- **"Closed derivation" means empty context and no derivation premise**: 190 declarations. The
  85 context-form declarations and 56 rules are outside the registration requirement. The check
  should print all three counts so the boundary is visible.
- **Registry by kernel-checked rows generated from the declaration's type** (design C); no
  attribute and no environment extension.
- **Fragment of a schematic statement is the profile of its instance at distinct atoms**
  (`stmt schemaVar`). An instance at atoms contains exactly the operators of the schema.
- **Conjecture statements are `Prop`s**, with fragment and cell declared, since the edges are
  not formulas.
- **`⊡` is a field of the profile, not a family**: `Profile.fragment` maps `box || stab` to
  Modal, as the record fixes.

## Risks & Mitigations

- **Environment linters on generated rows.** C16 of `check-module-invariants.sh` runs the
  Batteries linters over the lake library roots, and `docBlame` wants a docstring on every
  definition. Not measured here. Mitigation: `register_theorem` attaches a generated docstring
  (`addDocStringCore`), and the plan runs `lake exe runLinter BimodalLib` as a phase gate.
- **Package-level syntax linters under `--wfail`.** `weak.linter.mathlibStandardSet` applies to
  every library: file headers, module docstrings, no `#` commands outside the test libraries,
  the 1500-line limit. Mitigation: name commands without `#`; keep `#guard_msgs` tests in the
  test library.
- **The scan sees only imported modules.** A new file under `FormalSystem/Theorems/` that the
  root `FormalSystem.lean` does not import would escape. The root is generated to import
  everything and other checks guard that; the check module must import the root.
- **The dual listing is partly declarative.** No mechanical test decides in general whether a
  diamond law is the dual of a box law, because `◇` is `¬□¬` and the K-shaped laws do not
  dualize syntactically. A declared `dual :=` link with a computed polarity census is what can
  be built now; the listing will be long at first (21 `□`-only, 63 `G`-only, 68 `H`-only rows),
  which is the intended output.
- **Frame class above Base is an upper bound**, as stated above. The index should label the 16
  such rows "stated at", not "weakest".
- **The `PlusFormula` side has no rows yet.** No closed `PlusDerivationTree` is declared under
  `FormalSystem/Theorems/` outside `ProofMode/`. `profileP` and a substitution-class type should
  exist now for `theorem_library_stability_entries`; a `PlusTheoremEntry` row type can wait for
  that consumer, or be added now without rows.
- **Stale description elsewhere.** The description's remaining text agrees with the record;
  only the ruling request is stale.
