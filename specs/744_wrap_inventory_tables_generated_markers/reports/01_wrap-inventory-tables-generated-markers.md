## Findings

### 1. How the generator actually behaves (from `scripts/check-module-invariants.sh:279-619`)

- **Marker grammar**: `<!-- BEGIN GENERATED: inventory dir=<repo-relative> [rows=loose|subdirs|both|totals] [empty=skip|include] [filter=all|aggregators|non-aggregators] [cols=lines|files-lines] [desc=yes|no] [link=yes|no] [sort=name|lines-desc] -->` … `<!-- END GENERATED -->`. Only `dir=` is required; defaults are `rows=both`, `cols=lines`, `desc=yes`, `link=no`, `sort=name`. Markers inside a ``` fence are ignored (lines 556-559).
- **What survives regeneration** (`render_block`, lines 419-497): the existing header line and separator line are kept verbatim (so `| Module | Lines | Role |` headers survive); the trailing description cell is carried across **keyed by file/directory name** (backticks and link labels stripped by `row_key`); a row for a live file with no existing description gets `<!-- TODO: add description -->`; a row whose file no longer exists is **dropped silently, description included**, unless the path still resolves relative to `dir=` (a "pinned" row such as `../BXCanonical.lean`, which the simulation confirmed survives with its count refreshed).
- **Description extraction is the weak point**: `descriptions[key] = cells[-1]` where `cells` comes from `split_row`, a plain `body.split("|")`. A GFM-escaped `\|` therefore splits the cell, and only the text after the last `\|` survives. No existing generated block in the tree contains `\|` (sweep result), so this latent defect has never fired — RaySummary would be the first victim.
- **Ordering**: `live_loose_files` returns `sorted()` paths; `sort=lines-desc` is the only alternative. There is no "keep existing order" option. The header comment (lines 255-263) explicitly offers the `<!-- INVENTORY: hand-maintained (dir=…) -->` registration for "a table ordered by the layering rather than alphabetically" — but registration only audits row existence (`audit_hand_maintained`, lines 500-528), never counts, so it would not meet this task's goal.
- **Number rendering**: `"{:,}".format(n)` — thousands separators appear for any count ≥ 1,000.
- **Write semantics**: the whole file is rewritten with `"\n".join(out)` only when some block changed; trailing newline is preserved. `--check` exits 1 and names each stale file; the writer never runs in CI (header comment, lines 265-273).

## Decisions

- **D1 — `\|` in three RaySummary descriptions (recorded as a non-blocking `user_decision`).** Options: (a) rewrite the inline Lean notation in rows 41/43/45 so no `|` remains (e.g. `Fin \|w\|` → `Fin (card w)`), then wrap; (b) make `split_row` escape-aware with the verified one-line `re.split(r"(?<!\\)\|", body)` and wrap unchanged; (c) register RaySummary hand-maintained and wrap only KTypeSummary (does not meet the goal). **Recommended: (b)**, because (a) edits mathematical prose that five reconciling tasks have carefully aligned with the record and still leaves a silent-truncation landmine for every future `\|` in any of the 29 existing blocks — the same "green gate, wrong content" class this task exists to remove — while (b) changes 1 line, is verified byte-for-byte on all 16 rows, and alters neither the column set nor the row algorithm. The task's NON-GOAL ("no change to the generator's column set or algorithm") was written under the belief that preservation was already total; the plan should state this deviation explicitly and keep it to that one line. If the user prefers strict record compliance, (a) is the fallback and the three rows are enumerated above.
- **D2 — Row order and number format.** Accept alphabetical order and `{:,}` formatting as the price of machine ownership. Both READMEs' descriptions carry their own layer labels (`B1`, `B2a`, `B3b`, `Requirement (C)/(S)/(W)`, `Step 1′`…), and the only prose reference to the table (`RaySummary/README.md:380`, "see the module table above") does not depend on its order. A `sort=existing` option would be a real generator-algorithm change and is out of scope; note it as a possible follow-up only if the alphabetization is judged a readability regression after the fact.
- **D3 — Regeneration must be targeted while 812's files are stale.** Do not run bare `--emit-inventory` in-tree. Either (i) run it and immediately restore the three foreign files via the sanctioned path (`bash .claude/scripts/git-snapshot.sh --no-revert 744` then `git checkout -- README.md FormalSystem/README.md FormalSystem/Metalogic/README.md`), or (ii) regenerate the two blocks out-of-tree with the extracted-Python method from Findings §3 and splice the block bodies back. (i) uses only repo machinery and is preferred; the restore is a pathspec checkout the guard permits after a `--no-revert` snapshot. Stage and commit only the two target READMEs (plus `scripts/check-module-invariants.sh` if D1(b) is taken).
- **D4 — Sweep scope.** Scope item (3) makes wrapping the fitting tables in-scope, but 24 Tier-A files plus 8 Tier-B files is a different size of change from the two named targets. Recommended: land the two targets (and D1) as this task's core phases; add one further phase wrapping Tier A only if the planner judges the budget allows, otherwise spawn a follow-up task carrying the Tier A/B lists verbatim from this report. Tier C is report-only.
- **D5 — No Lean edits, no hand corrections outside wrapped blocks**, per NON-GOALS. The stale counts listed in §4 are left as found.
