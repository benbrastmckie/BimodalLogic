# BMLogic-Bench: Bimodal Logic Benchmark

## Dataset Summary

**BMLogic-Bench** is a formal reasoning benchmark for **bimodal logic TM** — a decidable logic
combining S5 modal logic (`□`, necessity) with linear temporal logic (`U`/`S`, Until/Since
operators). The dataset tests whether language models can determine whether a bimodal formula is
logically valid, serving as a rigorous testbed for formal reasoning beyond propositional logic.

The benchmark comprises 727 stratified evaluation problems spanning four difficulty tiers (easy,
medium, hard, very_hard) with near-equal valid/invalid balance (~47%/~53%). Three training
datasets provide 53,841 labeled problems generated by verified Lean 4 decision procedures, giving
ground-truth labels with machine-checkable proofs and countermodels.

**One-line loading**:
```python
from datasets import load_dataset
ds = load_dataset("logos-labs/bmlogic-bench")  # default config: benchmark test set
```

## Dataset Details

### Dataset Description

BMLogic-Bench is generated by the [BimodalLogic](https://github.com/benbrastmckie/BimodalLogic)
Lean 4 formalization project. The decision procedure is a verified tableaux-based algorithm; every
`valid` label is accompanied by a formal proof trace, and every `invalid` label includes a
countermodel. Labels are therefore provably correct by construction.

The four dataset configurations serve different use cases:

| Config | Split | Records | Purpose |
|--------|-------|---------|---------|
| `default` (bmlogic-bench) | test | 727 | Stratified benchmark, model evaluation |
| `bmlogic-c5` | train | 1,513 | Small training set, complexity ≤ 5 |
| `bmlogic-c7` | train | 49,904 | Large training set, complexity ≤ 7 |
| `proof-steps` | train | 2,424 | Proof step supervision, 36 theorems |

- **Curated by**: Benjamin Brastmckie (Logos Labs)
- **Language(s)**: English (documentation), formal logic notation (data)
- **License**: CC BY 4.0

### Supported Tasks and Leaderboards

- **Primary task**: Validity classification — given a bimodal formula, predict `valid` or `invalid`
- **Secondary task**: Proof step prediction — given a proof state, predict the next inference rule

### Languages

Documentation is in English. Formula strings use standard logic notation with Unicode symbols
(□ for necessity, U/S for Until/Since, ⊤/⊥ for top/bottom, → for implication).

## Dataset Creation

#### Source Data

All formulas were generated exhaustively up to the specified complexity bound using the Lean 4
`dataset_generator` executable from the BimodalLogic project. The decision procedure runs on each
formula and records the result with proof or countermodel evidence.

The benchmark (`bmlogic-bench`) was built through a four-step pipeline:
1. Generate axiom instances (anchor points for valid formulas)
2. Curate candidates from training data with stratified sampling
3. Oracle validation with the Lean 4 decision procedure
4. Finalization with difficulty-tier balancing

#### Data Collection and Processing

Formulas are enumerated via a breadth-first search over the grammar of bimodal logic TM. The
grammar includes propositional atoms (p, q, r, ...), logical constants (⊤, ⊥), negation, implication,
the S5 modality □ (box), and the temporal Until operator U. For each formula, the decision
procedure determines validity in the TM frame class (S5 × linear order).

#### Personal and Sensitive Information

The dataset contains no personal information. All formulas are abstract mathematical objects.

#### Curation Rationale

Bimodal logic TM provides a realistic, non-trivial reasoning domain that:
- Has a decidable but EXPTIME-complete validity problem
- Requires combining modal and temporal reasoning
- Has a clean formal semantics that admits mechanized verification
- Produces interpretable countermodels for invalid formulas

The benchmark difficulty distribution was chosen to challenge both fine-tuned models and prompted
LLMs: simple propositional tautologies are excluded, and the hardest tier includes formulas
requiring complex interaction between modal and temporal operators.

## Uses

### Direct Use

- **Model evaluation**: Test LLM/fine-tuned model ability to classify bimodal formula validity
- **Fine-tuning**: Use `bmlogic-c5` or `bmlogic-c7` as training data for formal reasoning
- **Proof step supervision**: Use `proof-steps` config to train proof step prediction models
- **Benchmark reproducibility**: Re-run the four-step pipeline to regenerate equivalent data

### Out-of-Scope Uses

- **Classical propositional logic benchmarks**: This dataset is specific to bimodal TM logic; do
  not use it to evaluate propositional-only reasoning
- **Open-ended generation**: The dataset is for classification/prediction, not formula generation
- **Legal or safety-critical applications**: Synthetic formal data only; not suitable for
  real-world formal verification without human expert review

## Data Fields

### bmlogic-bench Schema (13 fields)

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Record identifier (e.g., `bmlogic-bench-00001`), sequential |
| `split` | string | Always `"benchmark"` |
| `formula_str` | string | Human-readable unicode notation (e.g., `□(p → q)`) |
| `formula_ast` | object | Recursive JSON AST with `tag` discriminator |
| `frame_class` | string | Frame class (always `"Base"` in current release) |
| `label` | string | Decision result: `"valid"` or `"invalid"` |
| `proof_trace` | object\|null | Proof tree for valid formulas (height, axioms_used, rules_applied); null for invalid |
| `countermodel` | object\|null | Kripke countermodel for invalid formulas; null for valid |
| `pattern_key` | object\|null | Structural pattern key with named fields |
| `metrics` | object | Complexity metrics (see below) |
| `source` | string | Data source (`"production"`, `"axiom_instance"`, etc.) |
| `difficulty_tier` | string | `"easy"`, `"medium"`, `"hard"`, or `"very_hard"` |
| `benchmark_category` | string | `"sampled-valid"`, `"sampled-invalid"`, `"anchor-valid"`, `"anchor-invalid"` |

**metrics sub-fields**: `complexity` (int), `modalDepth` (int), `temporalDepth` (int),
`impCount` (int), `atomCount` (int), `decisionTimeMs` (float), `difficultyTier` (string).

### Training Schema (14 fields, bmlogic-c5 and bmlogic-c7)

All 13 benchmark fields except `source`, `difficulty_tier`, and `benchmark_category`, plus:

| Field | Type | Description |
|-------|------|-------------|
| `formula_sexpr` | string | Canonical S-expression (e.g., `(box (imp p q))`) |
| `formula_tokens` | array | Prefix-notation token list for transformer tokenization |
| `pattern_features` | array\|null | Flat numeric feature vector `[modalDepth, temporalDepth, impCount, atomCount, complexity]` |
| `augmentation` | object\|null | Augmentation metadata (null for base data) |

Training `label` values: `"valid"`, `"invalid"`, or `"timeout"` (decision procedure exceeded time limit).

### proof-steps Schema (8 fields)

| Field | Type | Description |
|-------|------|-------------|
| `theorem_name` | string | Name of the theorem being proved |
| `step_index` | int | Zero-based step index within the proof |
| `context` | array | List of hypothesis formulas in scope |
| `goal` | object | Current proof goal as JSON AST |
| `rule` | string | Inference rule applied: `modus_ponens`, `axiom`, `necessitation`, `temporal_necessitation`, `temporal_duality` |
| `axiom_name` | string\|null | Axiom name when rule is `"axiom"`, else null |
| `subgoals` | array | Subgoals produced after applying the rule |
| `frame_class` | string | Frame class (`"Base"`) |

## Data Splits

| Config | Split | Records | Valid | Invalid | Timeout |
|--------|-------|---------|-------|---------|---------|
| bmlogic-bench (default) | test | 727 | 340 (46.8%) | 387 (53.2%) | 0 |
| bmlogic-c5 | train | 1,513 | 64 (4.2%) | 1,397 (92.3%) | 52 (3.4%) |
| bmlogic-c7 | train | 49,904 | 1,687 (3.4%) | 46,717 (93.6%) | 1,500 (3.0%) |
| proof-steps | train | 2,424 | — | — | — (36 theorems) |

**Total**: 54,568 records across all configs.

The low valid fraction (3-4%) in training data is expected: the space of arbitrary bimodal formulas
is overwhelmingly invalid. The benchmark achieves ~47% valid through stratified sampling with
targeted inclusion of axiom instances (anchor-valid category).

## Considerations for Using the Data

### Social Impact of Dataset

Bimodal logic TM has applications in AI planning, knowledge representation, and temporal reasoning
systems. Benchmarking LLMs on formal reasoning tasks reveals the extent to which these models can
perform structured, multi-step logical inference. The synthetic nature of the data means the
benchmark is free from demographic bias or sensitive content.

### Discussion of Biases

- **Class imbalance**: Training data is ~4% valid, while the benchmark is ~47% valid. Models
  trained on raw training data without reweighting will be biased toward predicting `invalid`.
- **Frame class**: All current data uses the `"Base"` (TM) frame class. Models may not generalize
  to other frame classes (e.g., reflexive-only, linear-time-only).
- **Complexity ceiling**: Training formulas have complexity ≤ 7 (c7) or ≤ 5 (c5). Benchmark
  formulas extend to complexity 15+. Generalization to higher complexity is an open research question.
- **Synthetic distribution**: Formulas are generated exhaustively/by sampling, not from natural
  mathematical texts. The distribution may differ from formulas humans would naturally write.

### Other Known Limitations

- The `"timeout"` label (3-4% of training data) indicates the decision procedure exceeded its
  time limit. These records have null `proof_trace` and null `countermodel`. Exclude them for
  clean binary classification tasks.
- Proof traces are available only for `valid` formulas. Countermodels are available only for
  `invalid` formulas. Neither is available for `timeout` records.
- The `proof-steps` config contains only 36 theorems; it is a supervision signal, not a
  comprehensive theorem library.
